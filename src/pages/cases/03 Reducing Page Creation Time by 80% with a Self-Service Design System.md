#### **Overview**

Supporting a large multilingual corporate website meant working with three very different user groups: content managers, marketers, and developers.

Over time, the same problem kept resurfacing. Creating new pages was slow, content teams struggled to choose the right components, and developers were repeatedly pulled into routine support requests. Even simple content updates often required back-and-forth communication between teams.

I saw an opportunity to reduce this dependency by creating a self-service tool that would help non-technical users build pages confidently without involving developers.

---

#### **The Challenge**

The company already had documentation for UI components, but it wasn't solving the real problem.

Existing design-system tools were maintained separately from the website, were primarily useful for developers, and didn't accurately reflect what users actually saw in the CMS. For content teams, they functioned more as showcases than practical working tools.

As a result:

- content managers often struggled to find the right component for a task
- new page sections required frequent developer involvement
- configuration mistakes were common
- page creation took between one and two days for typical content pages

The problem wasn't the lack of components. It was the lack of a usable system for discovering and applying them.

---

#### **The Solution**

Instead of creating another external documentation site, I proposed building the design catalog directly inside the existing Umbraco environment.

This approach ensured that every component in the catalog used the same templates, styles, and scripts as the production website. What users saw in the catalog was exactly what would appear on a live page.

The catalog was organized around real content-management tasks rather than technical implementation details.

I grouped components by purpose, created dedicated sections for common page-building scenarios, and added practical guidance for each block, including configuration recommendations and usage examples.

Components were organized around real content scenarios rather than technical implementation details. Instead of browsing a long list of available modules, content managers could start with their goal and quickly identify the most suitable building blocks.

---

#### **Result**

The catalog quickly became the primary reference tool for content managers, marketers, designers, and developers.

The impact was measurable:

- page creation time decreased from **1–2 days to 1–2 hours**
- support team productivity increased by **40%**
- dependency on developers for routine page creation was significantly reduced
- communication overhead between teams decreased

The solution proved successful enough that during the next website redesign I created a second-generation version of the catalog, which continued to evolve alongside the platform.

---

#### **Key Takeaway**

The biggest improvement did not come from adding new functionality. It came from making existing functionality easier to discover, understand, and use.

By focusing on the needs of internal users rather than the technology itself, we transformed a fragmented design system into a self-service product that scaled content operations across the organization.
